# Plan: Onboarding chat

From: intent.md (2026-10-16), spec.md (2026-11-04). Approved: Jordan Davis, 2026-11-04.

## Context

Signup is live but ends on a placeholder (`/welcome`). This builds the product's first real experience: a chat-led onboarding in a sheet over a new home screen. It covers three steps: your money story (chat), the Stryvv Score baseline (6 taps), and your rich life (chat). It saves confirmed money-history entries, goals and one baseline check-in, then lands the person on a minimal home with their score rings, goals and entries. The coach runs on Claude through the Vercel AI SDK. This file is saved as `docs/work/2026-10-16-onboarding-chat/plan.md` as the first step of the build and kept in step with what's built.

## Files that change

**Database (careful lane, one migration)**
- `supabase/migrations/20261104000100_onboarding.sql` (new):
  - a named check constraint on `profiles.onboarding_stage` (`not_started`, `money_story`, `baseline`, `rich_life`, `done`)
  - a unique partial index for one onboarding conversation per person
  - narrower grants:
    - `conversations`: update only `topic`; insert only `(kind, topic)`
    - `messages`: insert only `(conversation_id, role, content)`, so history can't be backdated
  - `public.record_baseline(answers jsonb) returns uuid`, written like `end_partnership()` (security definer, `search_path = ''`, `not_authenticated`). It:
    - requires exactly the six metric keys, each an integer 0–4, and raises `invalid_answers` otherwise
    - computes the three parts and the total (version 1, rounding as the framework says)
    - inserts the check-in and its 11 measurements in one transaction
    - turns a unique violation into `baseline_exists`
    - grants execute to `authenticated` only
- `supabase/tests/10_onboarding.sql` (new, written first), covering:
  - the best, worst and mixed score cases
  - all-or-nothing: a bad answer leaves no check-in
  - a second baseline is refused
  - missing, extra or out-of-range answers are refused
  - anon can't call the function
  - stage values are enforced
  - a second onboarding conversation is refused
  - `kind` and `created_at` can't be written
  - Uses `stranger@test.dev`, because the seeded owner already has a baseline.
- `supabase/tests/09_api_surface.sql` (edit): add `record_baseline` to the allowlist of callable definer functions.
- `lib/types/database.ts` (regenerated by `npm run db:types`).

**Logic (`lib/onboarding/`, not a `"use server"` folder, pure and tested)**
- `steps.ts`: the three steps and four story topics, plus two rich-life topics (what a rich life looks like, a first goal). For each topic: its opening question with an example answer, its answer chips (fixed per topic, e.g. how money felt), and its shortcut label ("Nothing comes to mind" / "Not right now").
- `flow.ts` + test: the topic pointer stored in `conversations.topic` (e.g. `story:2:7` = step, topic, and the user message count when the topic started). It provides:
  - `parsePointer` (anything invalid falls back to the start of the person's stage)
  - `userTurnsInTopic`
  - `mustAdvance` (three answers in a topic, or the shortcut, forces a move on)
  - `nextPointer`
- `score.ts` + `score-cases.ts` + test: the version 1 formula, the same as the SQL. The test also checks that every case in `score-cases.ts` appears in `10_onboarding.sql`, so the two copies can't drift apart.
- `baseline.ts`: the six items' wording and answer labels, from the framework.
- `prompts.ts` + test: the coach's system prompt, built from the step, topic, first name and remaining follow-ups. It includes the no-advice rule, one question at a time and short replies. Test: no last name or email ever reaches it.
- `schemas.ts` + test (Zod):
  - the chat request: text of 1–2,000 characters, the conversation id, an optional shortcut flag, and optional draft cards (capped at 12 cards, field lengths matching the table checks, at most 8 chips of 40 characters)
  - the `propose_money_history` and `propose_goals` tool inputs
  - the save-action inputs
- `limits.ts` + test: the pure decision on whether to send a message, given counts: at most 60 user messages a conversation and 20 a minute. Too many gets "Let's pause for a moment".

**Server**
- `app/api/onboarding/chat/route.ts` (new, the first route handler):
  1. Rejects anyone not signed in with 401, and validates the body.
  2. Loads the conversation and its messages through the session client; RLS limits it to the person's own.
  3. Checks the limits by counting `messages`.
  4. Saves the user's message before calling the model.
  5. Calls `streamText` with `@ai-sdk/anthropic` `claude-sonnet-5-5`:
     - `maxOutputTokens: 400`
     - the system prompt cached with `cacheControl`
     - `stopWhen: stepCountIs(3)`
     - Two tools:
       - `next_topic`: runs on the server and only advances the pointer in memory. Its result is the next topic's opening brief. It's forced when `mustAdvance` says so.
       - `propose_money_history` / `propose_goals`: no execute; the client renders the validated input as review cards.
  6. Calls `result.consumeStream()`, so the reply is saved even if the person closes the app.
  7. `onFinish` saves the reply text and the new pointer, and logs ids and token counts only.
  8. A request with no text but `intent: "propose"` re-proposes cards on resume.
- `lib/actions/onboarding.ts` (new, `"use server"`, actions only). Each one checks the user first.
  - `startOnboarding`: creates or gets the conversation, sets the stage to `money_story`.
  - `saveMoneyHistory(cards)`: inserts entries in one statement, skipped if this conversation already has entries, so a retry doesn't make duplicates. Then sets the stage to `baseline`.
  - `saveBaseline(answers)`: calls `record_baseline`. `baseline_exists` counts as success.
  - `saveGoals(cards)`: the same idempotency, then the stage moves to `done`.
  - `skipStep(step)`.
  - `reopenStep(step)`: from the home empty states. It sets the pointer and leaves the stage at `done`.
- `lib/supabase/proxy.ts` (edit): add `/home` to the signed-in pages; signed-in people land on `/home`. `/welcome` stays listed.
- `lib/actions/auth.ts` (edit): the four `redirect("/welcome")` calls go to `/home`.

**UI (`components/app/`, design-system tokens, light and dark)**
- `sheet.tsx` (new): a bottom sheet on `radix-ui` Dialog. The content carries `stryvv-app` and the font variables, because the portal renders outside `AppShell`. It's full-screen under a 40px gap on phones, and a centred panel up to 560px on desktop.
- `onboarding/` (new):
  - `onboarding-sheet.tsx` (client): the step controller. It uses `useChat` from `@ai-sdk/react` with `DefaultChatTransport`, and `prepareSendMessagesRequest` sends only the new text, the id and any draft cards.
  - The pieces: `step-header.tsx`, `chat-bubble.tsx` (coach text rendered through `markdownToHtml`), `chip-group.tsx`, `chat-composer.tsx` (stays above the keyboard; send is disabled while a reply streams), `review-card.tsx` (edit, note, remove), `save-bar.tsx`, `baseline-step.tsx` (one item at a time, tap answers, no model).
- `home/` (new): `ask-bar.tsx` (shows "Ask Stryvv is coming soon" when tapped), `module-card.tsx`, `score-rings.tsx` (an SVG overall ring plus three small part rings).
- `app/(app)/home/page.tsx` (new, server component):

  - Opens the sheet when the stage isn't `done`.
- `app/(app)/welcome/page.tsx` (edit): redirects to `/home`.

## Risks

- **The coach gives financial advice or wanders off the sequence.**
  - Guards: the server owns the step and topic pointer and forces `next_topic` after three answers; the system prompt carries the no-advice rule; and the manual proof asks the coach for investment advice and checks it declines.
- **Spend runs over the $0.10 budget.**
  - Guards: replies capped at 400 tokens, three steps per reply, the message caps, a cached system prompt, and the Anthropic spend limit.
  - The proof measures three full runs. If they run over, switch to `claude-haiku-5-5`, which is a one-line change.
- **A half-written baseline blocks the real one.**
  - Guard: `record_baseline` runs in one transaction, and the pgTAP all-or-nothing case covers it.
- **A retried save creates duplicate entries or goals.**
  - Guard: the save skips when rows for this conversation already exist, and the stage advances after the insert.
- **A reply is lost when the app closes mid-stream.**
  - Guard: `consumeStream()` plus saving in `onFinish`. The proof closes the tab mid-reply and resumes.
- **The person writes fake coach messages into their own history.** Without an admin client, the session can insert `role = 'assistant'`.
  - Accepted: it only affects their own conversation, and the coach has no tools that write data or read anyone else's. Noted in the PR.
- **Rate limits race.** Two parallel requests could each pass the count.
  - Accepted: the result is at most a message or two over the cap, and the Anthropic spend limit stops anything worse.
- **Design tokens are lost in the portal.**
  - Guard: `sheet.tsx` puts the `stryvv-app` class and the fonts on the portal content. Checked in light and dark.
- **The phone keyboard covers the message box.**
  - Guard: the composer uses `dvh` / `visualViewport`. Checked in mobile emulation.

## Changes while building (2026-11-04)

- **AI SDK pinned to the v6 line.** npm's `latest` is v7; the repo has `ai` v6, so `@ai-sdk/anthropic@3` and `@ai-sdk/react@3` (their `ai-v6` tags) were installed and `ai` bumped within v6 to match. Moving to v7 is its own change.
- **`profiles.rich_life_vision` added** to the migration, with tests, because the vision card needed somewhere to be saved (spec: Changes while building).
- **The pointer has four parts**, `step:topic:topicStart:stepStart`, so the route sends the model only the current step's messages (`messagesForStep`), which keeps each call cheap. `topicStart` counts the person's messages (for the three-answer cap); `stepStart` counts all messages, because a step skipped with no answers would otherwise start at the same place as the next one (caught in the browser: a reopened story showed step 3's opening).
- **`02_partner_sharing.sql` filters by owner** in its two unscoped reads (the seeded conversation, and the money-history check), so it passes on a local database that already has other accounts (it assumed an empty one).
- **No prompt caching** (the prompt varies per topic and is below the cacheable minimum).
- **Openings are written by the app.** Each step's first coach message comes from `steps.ts` (with the first name and an example answer) when the step starts, so opening a step costs no model call.
- **Extra files:** `lib/onboarding/server.ts` (database helpers for the actions and the route), `lib/onboarding/messages.ts` (UI message type), `lib/onboarding/format.ts` (goal amount and date), `app/(app)/home/loading.tsx` (skeleton cards), `components/app/onboarding/chat-step.tsx` (the chat and review controller).
- **No forced tool calls.** `claude-sonnet-5-5` always thinks and rejects forced tool use (the AI SDK silently falls back to `auto`), found in the first live run: "Nothing comes to mind" didn't move on. Now the server advances the pointer itself after three answers or the shortcut, and tells the coach the next question (`moveOn` in the prompt); the coach can still move on early with `next_topic`.
- **Review cards are structured output, not tool calls.** At a step's review the route calls `generateText` with `Output.object` (closed `z.strictObject` schemas, so Anthropic's native structured output is used) and sends the cards as a `data-proposal` part through `createUIMessageStream`. The `propose_*` tools are gone.
- **Token caps allow for thinking.** Thinking counts toward `maxOutputTokens`, and the first review hit the 400 cap mid-card. Replies are capped at 1,200 (kept short by the prompt) and reviews at 4,000, with `effort: "low"`.
- **Today's date reaches the coach,** so relative goal dates resolve ("by next June" became 2027-06-30; "in three years" became Nov 2029). Found in the live run, where "next June" was dropped.
- **Stronger sheet overlay** (dimmer, with a slight blur). On a short desktop window in dark mode, the home cards peeking out under the panel read as part of the sheet (Jordan's screen capture).

- **Relationship question and Unity at the baseline** (Jordan, after testing): `profiles.in_relationship`, `record_baseline` accepts six or eight answers, a partnered case in the shared score cases and `10_onboarding.sql`, and a Yes / No question before the taps.
